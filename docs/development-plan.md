# EnjoyTrip 명세 기반 설계와 TDD 개발 계획

PDF의 Web Front 과제를 HTML, CSS, JavaScript, Bootstrap으로 구현한다. 먼저 필수 요구사항을 검증 가능한 명세로 작성하고, 각 동작을 실패하는 테스트부터 개발한다. 구현 결과는 README와 specs/test-matrix.md에 기록한다. 현재 필수 데모 기능과 단위·DOM·E2E 검증을 마쳤으며 F101 실제 API 연동 검증은 남아 있다. 사용자 요청에 따라 단일 앱과 빌드의 모듈형 모놀리식으로 구성하며 AI·로그·검색 제공자는 src/contracts.js의 계약으로 확장한다.

## 근거와 범위

원문: 자바전공_enjoytrip_16_03_프론트.pdf, 16쪽. 3~4쪽은 기술과 작업 범위, 5~6쪽은 요구사항, 7~15쪽은 화면 예시, 16쪽은 제출물을 설명한다. 문서의 작업 지시와 외부 업로드 안내는 과제 참고자료로 취급한다. 후속 사용자 요청에 따라 필수 기능 구현과 확장 가능한 모놀리식 구조까지 진행한다. GitLab 업로드는 별도로 요청받았을 때 진행한다.

필터 초기화, 중복 식별자 거절, 보호 화면과 권한 규칙은 원문을 구체화한 제안이다. 비밀번호 길이 등 상세 정책은 구현 전에 기능 명세에서 확정한다. 원문 예시 화면은 참고 레이아웃이며 픽셀 단위 복제를 요구하지 않는다.

## 기술과 데이터 설계 제안

앱은 HTML5, CSS3, JavaScript ES modules와 Bootstrap을 사용한다. 프레임워크와 상태관리 라이브러리는 추가하지 않는다. 개발 서버는 Vite, 단위 및 DOM 테스트는 Vitest와 jsdom, 핵심 브라우저 흐름은 Playwright를 후보로 두며 착수 시 호환 버전을 확인하고 잠금 파일로 고정한다.

화면은 홈, 관광지 검색, 회원가입, 로그인, 내 정보, 비밀번호 찾기부터 만든다. 추가 기능에서 여행계획·Hotplace, 심화에서 게시판을 연결한다. 검색 UI → 관광정보 서비스 → 데이터 요청 함수의 단순한 의존 방향을 유지한다. 지도 연동은 작은 어댑터로 격리한다.

관광 데이터의 내부 필드는 contentId, title, areaCode, sigunguCode, contentTypeId, address, imageUrl, latitude, longitude로 통일한다. 외부 응답은 한 곳에서 변환하고 식별자는 문자열로 유지한다. API의 실제 버전·유형 코드·페이지 규칙·응답 형태는 공식 문서와 샘플 응답을 확인한 후 데이터 계약에 고정한다.

PDF의 한국관광공사 API와 SGIS API를 연동 후보로 사용한다. 먼저 고정 fixture로 테스트를 작성하고, 키 발급·도메인 등록·CORS·호출 제한을 확인한 뒤 실제 요청을 연결한다. fixture와 실제 데이터 모드는 화면과 README에서 구분한다. F101의 완료 판정에는 실제 공공데이터 연동 확인을 포함하며 fixture만 동작하면 부분 완료로 남긴다. 브라우저에 넣을 수 없는 비밀키가 필요하면 최소 프록시 도입을 별도 결정한다.

회원 기능은 과제용 로컬 데모로 계획한다. localStorage에는 버전이 있는 데모 계정·프로필 데이터를, sessionStorage에는 현재 데모 세션을 저장하는 방안을 검토한다. 실제 개인정보를 사용하지 않는다. 비밀번호 원문 조회 대신 데모 재설정으로 구현하며 실제 신원 확인·이메일 발송·서버 인증은 후속 서버 범위다. 이 제한은 화면과 README에 명시한다. 저장소 손상·쓰기 실패·버전 불일치의 처리도 명세한다.

## Spec Driven Development 산출물

| 문서 | 내용 | 완료 조건 |
| --- | --- | --- |
| specs/requirements.md | 필수·선택 범위와 원문 페이지, 요구사항 ID | 필수 F101~F103·F107·F108 누락 없음 |
| specs/features/*.md | 기능별 정상·실패·경계 시나리오와 상태 전이 | Given When Then 수용 기준 작성 |
| specs/data-contracts.md | 관광 데이터·회원·세션·저장소·외부 API 계약 | 필드와 오류 처리, 데모 제한 명확화 |
| specs/ui.md | 화면 흐름, 폼, 로딩·빈 결과·오류, 반응형 | 데스크톱·모바일·키보드 이동 정의 |
| specs/test-matrix.md | 요구사항 → 수용 기준 → 테스트 파일 매핑 | 필수 시나리오 모두 테스트에 연결 |
| docs/decisions.md | 확정한 정책과 이유 | 미정 항목과 결정 내용을 구분 |

변경 순서는 요구사항 변경 → 명세와 테스트 매핑 수정 → 실패 테스트 → 최소 구현 → 리팩터링이다. 구현만 수정해 명세를 뒤따라 맞추지 않는다. 문서 구조는 위 수준으로 시작하고 필요 없는 별도 계층은 만들지 않는다.

## TDD 개발 순서

각 기능은 Red → Green → Refactor로 진행한다. 실패 테스트가 원하는 이유로 실패하는지 확인하고, 가장 작은 구현으로 통과시킨 뒤 중복을 정리한다. 실제 네트워크와 지도 SDK는 자동 테스트에서 대체하고 별도 연동 점검으로 확인한다.

| 단계 | 먼저 작성할 테스트 | 구현 결과와 종료 조건 |
| --- | --- | --- |
| 0 명세 확정 | 테스트 매핑 작성 | 필수 범위, 회원 정책, 데이터 모드 결정 |
| 1 실행 환경 | 테스트 실행 smoke 확인 | 개발 서버와 단위·DOM·E2E 실행 경로 준비 |
| 2 관광정보 로직 | 지역·유형 결합, 전체 선택, 빈 응답, 필드 누락 | F101~F103 데이터 변환·조회 로직 통과 |
| 3 관광 검색 UI | 폼 제출, 로딩, 목록, 빈 결과, 오류, 늦은 응답 | 이전 요청이 새 검색 결과를 덮어쓰지 않음 |
| 4 회원·세션 | 잘못된 입력, 중복, 로그인 실패·성공, 수정, 탈퇴, 로그아웃, 재설정 | F107~F108 정상·실패 흐름 통과 |
| 5 필수 통합 | 가입 → 로그인 → 조회 → 수정 → 로그아웃 → 재로그인 → 탈퇴 | 브라우저 새로고침과 저장소 복원까지 검증 |
| 6 실데이터·품질 | 외부 응답 계약 fixture 및 실패 처리 | 실 API 수동 점검, 반응형·키보드·에러 안내 확인 |
| 7 선택 기능 | 일정 순서·저장 복원, Hotplace 입력·이미지 제한 | 필수 통과 후 F104·F105 진행 |
| 8 심화·제출 | 게시판 CRUD·권한·빈 상태 | 선택한 심화만 구현하고 README·캡처 완성 |

예시 F102 수용 기준: Given 제주 지역과 음식점 유형이 선택되어 있을 때, When 검색하면, Then 두 조건을 만족하는 결과만 표시한다. 실패 응답이면 로딩을 종료하고 재시도 안내를 표시한다. 이 기준을 서비스 단위 테스트와 DOM 테스트에 연결한다.

예시 F107 수용 기준: Given 이미 가입한 식별자가 있을 때, When 같은 식별자로 가입하면, Then 계정을 추가하지 않고 해당 입력 옆에 오류를 표시한다. 회원 탈퇴 시 계정과 현재 세션을 함께 제거한다.

## 비기능 요구사항과 완료 기준

NF101은 필드별 오류, 명확한 버튼·상태 안내와 일관된 탐색으로 확인한다. NF102는 제안한 360px·768px·1440px 화면 폭에서 가로 넘침 없이 주요 흐름을 수행하는지 확인한다. NF103은 중복 요청 방지, 검색 중 상태 안내, 오래된 응답 무시를 검사한다. 고정 응답시간 수치는 API 특성과 측정 조건을 확인한 후 정한다. NF104는 데이터 출처·기준 시점과 fixture 여부를 명시하고 외부 응답을 검증한다.

필수 요구사항의 모든 수용 테스트가 통과해야 MVP 완료다. 회귀 테스트, 실제 관광 API 연동, 반응형 점검, 키보드 조작, 로딩·빈 결과·실패 UI까지 확인한다. CSS 클래스나 함수 내부 구현을 그대로 따라가는 테스트 대신 사용자 행동과 결과를 검증한다. 코드 리뷰 그래프는 영향 범위와 누락 테스트 탐색에 사용하며 테스트 통과를 대체하지 않는다.

README에는 실행·테스트 방법, 구현한 요구사항 ID, 실데이터 설정, 데모 회원 제한, 미구현 기능을 적는다. 필수 화면과 모바일 화면 캡처를 제출 산출물로 만든다.

## 예상 일정

PDF의 기준은 필수 5시간, 추가 2시간, 심화 1시간이다. 이 계획의 시간 배분은 추정이며 도구 설치·키 발급 대기·외부 연동 장애는 제외한다.

필수 5시간은 명세 45분, 실행·테스트 환경 30분, 관광 검색 90분, 회원·세션 90분, 통합·품질·README 45분으로 배분한다. SDD와 TDD가 처음이면 필수 단계부터 시간을 늘리고 선택 기능을 줄인다. 추가 2시간은 여행계획 75분과 Hotplace 45분, 심화 1시간은 게시판 하나를 우선한다. 실제 크롤링과 DB까지 1시간에 완료한다고 가정하지 않는다.

## 설치 도구 운용

- Caveman 3.0.0: Codex 플러그인 설치 완료. 필요할 때 간결한 설명에 사용한다.
- Ponytail 4.10.0: 기존 설치와 활성화 확인. 불필요한 의존성·추상화를 줄이되 명세와 TDD 요구를 우선한다.
- code-review-graph 2.3.9: 프로젝트 `.tools/crg` 가상환경에 설치, Codex MCP와 hooks 등록 완료. Codex 재시작 후 MCP 로드를 확인한다. 아직 앱 소스가 없어 그래프 데이터와 리뷰 효과는 검증 대상이 아니다.
- 기존 CodeGraph는 별도 도구다. 사용자 지침대로 `.codegraph/`가 있을 때만 우선 사용하며 이번에 인덱스를 만들지 않는다.
- 소스 작성 후 `.tools/crg/Scripts/code-review-graph.exe build --repo .`로 최초 그래프를 만들고 리뷰 전에 update한다. 현재 Git 저장소가 없어 Git hook은 설치되지 않았다. Git 초기화 후 필요하면 설치 명령을 재실행한다.
- `.tools/`는 로컬 도구이며 커밋하지 않는다. 다른 개발자는 자신의 환경에 도구를 설치하고 MCP 경로를 설정해야 한다.
